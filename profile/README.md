<p>检测不是打开一个查询页看结果，而是四层交叉验证。本文先讲该查哪四个字段，再给查询入口和命令，然后是一张判定表，接着讲三天跟踪法和常见误判，最后说明怎么把检测做成例行工作，附常见问答。</p>
<h2>一、要查的四个字段</h2>
<p>国家与城市、ASN 与运营商名、使用类型、历史标记。前三个是相对静态的属性，查一次就够；第四个会随时间变化，需要定期复查。</p>
<p>四个字段里 ASN 最能说明问题。ASN 属于本地运营商，说明地址在运营商网络里真实分配；ASN 属于云厂商，这段地址本质就是机房段，只是登记库更新慢。</p>
<h2>二、查询入口和命令</h2>
<p>网页端用两三个不同的查询站交叉看，避免单一库滞后。命令行用 whois 查段归属，用 curl 调公开接口拿结构化字段，结果好存档也便于批量比对。</p>
<p>批量查的时候写个循环，把结果存成表格，比一个个点网页可靠。查完存档，后面出问题时才有基线，否则只能凭印象判断。</p>

<h2>三、判定表怎么读</h2>
<p>五项全过，可以按住宅地址使用。ASN 或使用类型一项不过，说明画像与宣传不符，先找服务方确认，别急着配业务。</p>
<p>历史标记不过但其他都过，属于可用但要观察。标记多来自采集或批量注册，短期高频操作容易被关联，配业务时把节奏放缓一些。</p>
<h3>为什么两个查询站结果不同</h3>
<p>各家库的更新频率和判定规则不同。新划分的段在一家显示机房、另一家显示住宅很常见。以多个来源的多数结果为准，并把差异记进档案。</p>
<h2>四、三天跟踪法</h2>
<p>第一天开通即查，记录地址与延迟。之后每天同一时段各查一次，连查三天。三天地址不变，可以按静态使用；中途变了说明是动态池，配置时别写死。</p>
<p>延迟一起记。三天延迟均值稳定、抖动小于两成，线路质量算合格。抖动大的先查是不是共享带宽，再查跨境段的拥塞时段。</p>
<h2>五、检测里的常见误判</h2>
<h3>最常见的四种错法</h3>
<p>一是把“住宅”当成唯一标准。二是只看一次结果。三是用本机浏览器直接访问查询站，忘了浏览器可能不走代理，查到的是自己的地址。</p>
<p>四是忽略 DNS。地址是美国、解析走本地，这种错配在部分平台上比地址本身更容易被注意到，尤其配合账号登录地一起看的时候。</p>

<h3>浏览器检测的正确姿势</h3>
<p>开无痕窗口，确认代理已生效，先访问一个显示出口地址的页面，再打开查询站。两次显示的地址应该一致，不一致就是代理没全覆盖。</p>
<h2>六、把检测做成例行工作</h2>
<p>开通时做一次完整检测并存档，之后每周复查地址与延迟，每月复查历史标记。有基线，异常才好判断，也方便和服务方沟通。</p>
<p>出现账号异常时，先回看检测记录，确认是地址变了、延迟抬升，还是操作行为变了。三类原因的处理方式完全不同，别一上来就换地址。</p>
<h2>常见问答</h2>
<h3>只查一个网站够不够？</h3>
<p>答：不够。单一库可能滞后，两到三个来源交叉看更可靠，新划分的地址段尤其容易出现一家一个结果。</p>
<h3>ASN 显示运营商就一定是住宅吗？</h3>
<p>答：不是。运营商也会有机房类业务段。还要看使用类型字段和实际分配方式，两项一起看才准。</p>
<h3>检测出地址变了怎么办？</h3>
<p>答：先确认是套餐本身就是动态，还是故障切换。动态套餐属正常现象，故障切换要找服务方查线路。</p>
<h3>有没有一键检测的工具？</h3>
<p>答：有，但多数只查归属，不查历史标记和 DNS 出口。按四项自己分开查，结论更清楚，也便于留档。</p>
